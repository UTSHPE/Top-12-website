# Supabase schema

Ground truth for the `public` schema behind the Top 12 app.

**How this was produced.** The `SUPABASE_SERVICE_ROLE_KEY` in `.env.local` is
currently rejected by the project (`401 Invalid API key`), and PostgREST only
exposes its OpenAPI spec to `service_role`. Everything below was therefore
verified with the **anon** key by probing each column individually — requesting
a column that does not exist returns Postgres error `42703`, which is a reliable
existence check.

That method proves **which columns exist**. It cannot see constraints, foreign
keys, nullability, defaults, or RLS policies. Those are marked
_unverified_ below. To fill them in, run `docs/migrations/000_introspect.sql`
in the Supabase SQL editor and paste the output back here.

Last verified: 2026-08-03.

## Tables

There are exactly three tables in `public`. PostgREST returns `PGRST205` for
`attendance`, `check_ins`, `checkins`, `users`, and `officers` — and helpfully
suggests `sign_ins` / `members` as the nearest matches. **There is no separate
attendance table; `sign_ins` is it.**

**On `sign_ins.eid`:** `lib/leaderboard.ts:50` falls back to the raw EID
"so an orphaned sign-in still shows up", which implies there is no FK to
`members`. This is an inference from application code, not a verified

unknown EID is even insertable — the app rejects those before attempting an
insert, so the behavior is the same either way.

## Row-level security

**Verified:** RLS is **enabled on `sign_ins`**. An anon `INSERT` returns:

```
42501  new row violates row-level security policy for table "sign_ins"
```

**Verified:** anon `SELECT` on `events`, `members`, and `sign_ins` all return
`200` with an empty array. This is ambiguous — it means either the tables are
empty or RLS is filtering every row. It cannot be resolved without working
`service_role` credentials.

**Unverified:** the actual policy definitions on all three tables, and whether
RLS is enabled on `events` and `members` at all.

This is worth resolving. `members` holds names, emails, and student EIDs; if
RLS is off there, the public anon key can read the entire roster.

## Access patterns

Server-side reads use `createAdminClient()` (`lib/supabase/admin.ts`), which
holds the service-role key and bypasses RLS. It must only ever be called from
Server Components, server actions, or route handlers — never from a client
component, and the key must never reach a `NEXT_PUBLIC_` variable.

The browser client (`lib/supabase/client.ts`) uses the anon key and is used
only for officer auth.

Because every read goes through the service-role client, **an invalid service
role key makes the whole app render as empty rather than erroring** — the query
helpers all use `data ?? []` and discard the error. If the events grid,
leaderboard, and officer dashboard are all simultaneously blank, check the key
before looking anywhere else.
